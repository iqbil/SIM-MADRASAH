BAB I. PENDAHULUAN DAN BATAS CAKUPAN
1.1 Latar belakang dan tujuan
SIM memusatkan administrasi madrasah agar data siswa, pegawai, akademik, kehadiran, honor, soal, BK, surat, dan publikasi tidak terduplikasi. Sistem menyediakan proses yang dapat ditelusuri serta akses sesuai tugas. Portal wali dan dashboard pimpinan menggunakan sumber data operasional yang sama.
1.2 Cakupan
Termasuk rilis awal penuh (bertahap)	Default fitur lanjutan / nonaktif
Akun pegawai/wali, master, periode, kelas, penugasan dan jadwal.	Akun siswa dan PPDB nonaktif; hanya identitas siswa tanpa login. Multi-madrasah di luar cakupan.
Absensi pegawai/siswa harian, realisasi/verifikasi, rekap.	Input web satu shift; foto + GPS aktif hanya untuk masuk/pulang pegawai. Biometrik dan absensi siswa pertemuan/both tetap nonaktif.
Perhitungan, pemeriksaan, pengesahan/penguncian honor dan adjustment.	Pembayaran digital, pencatatan status bayar, SPP dan akuntansi menyeluruh di luar cakupan.
Bank soal, paket PDF, BK dan surat/arsip.	Ujian online, nilai/rapor, DOCX, co-teaching dan disposisi nonaktif.
Portal wali, website, dashboard, ekspor, audit dan restore.	Integrasi otomatis EMIS tidak tersedia; pertukaran data melalui impor/ekspor berizin.
Notifikasi in-app untuk pengumuman dan perubahan status penting.	Kanal eksternal email/WhatsApp/SMS nonaktif sampai penyedia, biaya, dan persetujuan penerima ditetapkan (DEC-20).

1.3 Asumsi dan dependensi
Asumsi: satu madrasah, akses web melalui komputer/ponsel, tim pengelola kecil. Multi-madrasah tidak termasuk kecuali cakupan diubah.
Aturan awal honor, kewenangan, kalender kerja, pola absensi, notifikasi dan privasi mengikuti default DEC-01–DEC-21. Nominal tarif, identitas pejabat dan kalender akademik adalah data onboarding; sistem menyediakan konfigurasi bertanggal/berversi untuk perubahan berikutnya.
Kebutuhan bisnis dipisahkan dari teknologi; arsitektur Laravel API dan Next.js/React pada Bab VIII menjadi baseline yang ditetapkan untuk pengembangan ini.
ERD fisik, kamus data, migration dan batas implementasi dijabarkan di backend/database/database.MD; tampilan mengikuti design-system.md, sedangkan status pengerjaan mengikuti roadmap-agents.md.
1.4 Konvensi kebutuhan
FR = kebutuhan fungsional; BR = aturan bisnis; NFR = kebutuhan kualitas; AC = kriteria penerimaan; DEC = default implementasi berversi. FR-xx mempertahankan ID modul sumber. Seluruh DEC berlaku sebagai baseline v1.4; fitur bertanda nonaktif disimpan sebagai backlog. Perubahan default selanjutnya tidak menimpa transaksi atau snapshot historis.

2.2 Matriks akses default
Matriks ini membedakan tindakan dan cakupan data. Verifikator akademik, pemeriksa/pengesah honor serta editor/penerbit mengikuti DEC-01/06/10. Mandat diberikan kepada akun nyata saat onboarding; role admin atau kepala tidak otomatis membuka BK internal atau seluruh honor.
Objek / proses	Pelaksana dan tindakan	Batas akses / pengesahan
Akun dan izin	Operator membuat/menonaktifkan; pengguna mengubah sandi sendiri.	Pemberian izin sensitif sesuai mandat; semua perubahan izin diaudit.
Siswa/kelas/penugasan	Operator mengelola; guru/wali kelas membaca.	Guru pada penugasan aktif; wali kelas pada kelas dan periode terkait.
Absensi pegawai	Pegawai mencatat masuk/pulang; petugas berizin mencatat status izin/sakit/cuti/dinas luar.	Pegawai melihat miliknya; koreksi oleh petugas berizin dengan alasan.
Realisasi mengajar	Guru pelaksana mengajukan; petugas akademik bermandat menyetujui/menolak, bukan pengaju yang sama.	Pertemuan yang ditugaskan; verifikator berdasarkan cakupan mandat.
Absensi siswa	Guru/wali kelas/petugas yang ditunjuk mencatat.	Kelas dan periode penugasan; wali melihat anaknya sendiri.
Honor	Bendahara membuat; pemeriksa bermandat meninjau; kepala bermandat mengesahkan, tiga akun berbeda.	Pegawai melihat hasil final miliknya; pihak lain hanya cakupan mandat. Default tidak menampilkan draft ke wali/pegawai umum.
Bank soal/kunci	Guru mengelola soal milik/penugasannya; pengelola paket merakit.	Akses kunci dan ekspor dipisahkan dari akses naskah.
Catatan internal BK	Guru BK sesuai izin khusus.	Operator, wali kelas, orang tua dan kepala tidak otomatis memperoleh akses.
Ringkasan BK dibagikan	BK menetapkan ringkasan dan penerima.	Wali kelas/wali hanya melihat ringkasan yang diberikan kepada mereka.
Arsip TU	TU membuat/mengelola surat dan arsip; disposisi nonaktif.	Kategori dokumen dan izin unduh; publik hanya dokumen terbit.
Konten website	TU/operator membuat draf; penerbit bermandat berbeda dari editor menyetujui.	Pengunjung hanya konten terbit; dokumen privat tetap tertutup.
Dashboard/ekspor	Pimpinan atau petugas berizin membaca/mengekspor.	Cakupan sama dengan data sumber; ekspor tidak memperluas izin.

2.3 Prinsip wajib
Otorisasi diperiksa di server pada setiap baca/tulis, pencarian, ekspor, API, dan unduhan; menutupi tombol tidak cukup.
Cakupan data menggunakan peran + penugasan + periode + hubungan wali–siswa. Akses yang tidak diberikan ditolak.
Pencabutan penugasan atau hubungan wali harus mengakhiri akses sesuai periode efektif tanpa menghapus riwayat.
Tidak memakai bypass administrator umum untuk catatan BK dan honor. Akses dukungan darurat, jika diperlukan, harus terbatas, beralasan, dan diaudit.
Pembuat, pemeriksa dan pengesah honor harus tiga akun berbeda. Verifikator realisasi tidak menyetujui pengajuannya sendiri. Baseline tidak menyediakan bypass; perubahan pemisahan tugas harus menjadi revisi kebijakan eksplisit dengan audit.

BAB III. KEBUTUHAN FUNGSIONAL TERPERINCI
Semua kebutuhan berikut merupakan baseline pengembangan v1.4. Fitur nonaktif berada pada backlog sesuai §1.2 dan DEC. Validasi server, pesan kesalahan dan otorisasi objek wajib pada semua modul.
3.1 Autentikasi dan pengguna (FR-01)
ID	Kebutuhan
FR-01-01	Login dengan username atau email dan password melalui Laravel API /api/v1/auth. Guard api memakai JWT HS256; akun dan identitas person harus aktif, multi-peran didukung, dan akun siswa-only tetap ditolak. Logout mencabut sesi JWT di server.
FR-01-02	Sandi dihash oleh Laravel. Pembuatan akun dan reset oleh petugas berizin menghasilkan sandi sementara 24 jam, sekali login, lalu wajib diganti; sesi terbatas hanya boleh membaca profil, mengganti sandi, atau logout. Ganti sandi memerlukan sandi lama, konfirmasi, minimal 12 karakter dengan huruf besar/kecil dan angka, maksimal 72 byte; seluruh sesi dicabut setelah berhasil. Pemulihan mandiri melalui tautan email belum tersedia.
FR-01-03	Batasi login 5/menit per kombinasi login+IP dan 20/menit per IP; refresh 30/menit per IP, Google 10/menit per IP, ganti sandi 5/menit per akun. Audit login, refresh/replay, logout dan pengelolaan akun. Perubahan password/status/email dan tindakan reset/pencabutan sesi membatalkan sesi sesuai layanan yang berlaku.
FR-01-04	JWT memiliki claim iss/aud/sub/sid/jti/iat/nbf/exp dan token_use=access. Access token default 15 menit. Refresh token acak 32 byte hanya disimpan sebagai hash SHA-256; rotasi sekali pakai mengganti JWT/jti dan refresh, tanpa memperpanjang batas absolut 120 menit. Replay refresh mencabut seluruh sesi terkait; logout-all tersedia pada API Laravel.
FR-01-05	Google OAuth opsional memakai Socialite, state satu kali, PKCE dan masa transaksi 10 menit. Hanya akun lokal aktif dengan email terverifikasi yang sama dan tanpa kewajiban ganti sandi dapat masuk. Tautan provider/subject dibuat pada login Google pertama yang sah; akun baru tidak didaftarkan otomatis. Subject berbeda untuk tautan yang sama ditolak; token Google tidak disimpan.
FR-01-06	Next.js BFF menjembatani /api/auth/* dan /api/accounts/* ke Laravel. JWT dan refresh hanya pada cookie HttpOnly; JSON yang diterima UI tidak berisi token. Mutasi memeriksa Origin dan JSON; transaksi Google memakai cookie madrasah_google maksimal 600 detik pada Path=/api/auth/google, lalu dihapus setelah callback.
FR-01-07	DatabaseSeeder menjalankan ReferenceDataSeeder dan SuperAdminSeeder; AccountAccessSeeder menyediakan 10 role awal termasuk super_admin dan katalog 45 izin terkelola (10 accounts.*, 31 master.*, 3 attendance.*, realizations.verify). INITIAL_ADMIN_EMAIL/NAME/USERNAME/PASSWORD dibaca langsung oleh SuperAdminSeeder. Jika password kosong, seeder memberi hash sandi acak yang tidak ditampilkan agar akun awal dapat memakai Google; konfigurasi Google wajib tersedia. Seeder tidak mengubah akun lama dan berhenti bila sudah ada grant Super Admin.
FR-01-08	Pengelolaan akun /api/v1/accounts mencakup daftar/detail/pembuatan/perubahan akun, status, role dan katalog izin terkelola, verifikasi email dengan pemeriksaan identitas, reset sandi sementara untuk akun lain, pencabutan sesi, pemutusan Google, audit serta konflik lock_version. UI tidak menawarkan hapus fisik akun atau pendaftaran publik. API role memuat katalog 45 izin terkelola: 10 accounts.*, 31 master.*, 3 attendance.* dan realizations.verify. Pemberian dibatasi kewenangan pemberi dan role sistem dilindungi. UI saat ini memfilter katalog dengan permissions dari auth/me (akun/master/akademik); attendance.* dan realizations.verify belum menjadi pilihan UI. Editor academic.* dan administrasi mandat juga belum tersedia. Mandat bertanggal/bercakupan tetap diperiksa di layanan domain, bukan digantikan pemberian izin role.
Status 27 Oktober 2026: FR-01–FR-07 sudah memiliki API, BFF/UI dan tes sesuai §1.5. Menu domain FR-08–FR-17 masih backlog; dashboard role awal bukan laporan lintas domain. Pemulihan mandiri via email, pengaturan mandat domain melalui UI, serta penetapan sandi pertama untuk akun Google-only tanpa sandi lama belum tersedia. Production TLS, konfigurasi Google nyata dan UAT tetap perlu validasi operasional.

3.5 Absensi pegawai (FR-05)
ID	Kebutuhan
FR-05-01	Catat masuk/pulang pegawai menggunakan waktu server; setiap aksi normal wajib foto baru dari kamera dan GPS perangkat. Petugas tetap mencatat izin, sakit, cuti, dinas luar sesuai referensi tanpa mewajibkan foto/GPS kehadiran. Absensi siswa tetap dicatat guru/wali kelas.

Default akurasi maksimal 100 m dan usia foto/lokasi maksimal 60 detik. Geofence opsional dapat diaktifkan per versi kebijakan sesuai FR-05-08; policy lama tetap tanpa geofence. Kamera/GPS gagal atau tidak diizinkan menolak aksi normal; tidak ada fallback diam-diam.
FR-05-05	Server memvalidasi foto lalu mengompresi sebelum penyimpanan final: WebP, sisi terpanjang 1.280 px tanpa upscale, kualitas awal 80 sampai minimum 60 untuk maksimal 300 KiB; EXIF dihapus setelah orientasi diperbaiki. files menyimpan metadata hasil, employee_attendance_captures menyimpan FK, ukuran input, dimensi/kualitas aktual serta snapshot policy. Byte foto bukan isi database.
FR-05-06	Policy foto/GPS/geofence dan DEC-16 dibuat sebagai versi efektif baru; data/policy lama tidak ditimpa dan tidak diwajibkan foto/GPS retroaktif. Akses bukti dibatasi ke pemilik/petugas absensi bermandat. Koreksi administratif tetap mengikuti alasan, approval berbeda dan audit; bukti asli dipertahankan.
FR-05-07	Sediakan SOP fallback administratif untuk kegagalan kamera/GPS: petugas bermandat mencatat kehadiran dengan status dan alasan tanpa membuat bukti foto/GPS; petugas penanggung jawab dan kanal bantuan ditetapkan pada onboarding sebelum addendum foto/GPS berlaku operasional. Aplikasi menampilkan petunjuk pemulihan (izin kamera/lokasi, sinyal, ulangi pengambilan) saat aksi normal gagal.
FR-05-08	Pengelola institusi dengan izin attendance.manage (Operator/Super Admin, role berizin eksplisit atau mandat institusi; mandat kelas/semester/pegawai tidak cukup) mengatur satu lokasi per versi kebijakan: nama, latitude, longitude dan radius 25–5.000 meter melalui peta Leaflet/OpenStreetMap. Klik/geser pin langsung mengisi koordinat dan lingkaran radius; input koordinat manual dan pemakaian lokasi perangkat secara eksplisit tersedia. Simpan memerlukan alasan, pemeriksaan policy terakhir, dan tanggal efektif mulai besok/setelah policy terjadwal terakhir. Tampilan membedakan policy berlaku dan terjadwal. Geofence hanya aktif setelah dikonfigurasi eksplisit; migrasi tidak menebak lokasi madrasah. API menghitung jarak Haversine (radius bumi 6.371.008,8 m) dan hanya menerima jika jarak + accuracy_meters <= radius. Jika jarak - accuracy_meters > radius, tampilkan alert di luar radius; kondisi tumpang tindih batas diberi alert posisi belum pasti. Keduanya menonaktifkan submit dan ditolak server 422 tanpa absensi/foto parsial. GPS diambil ulang sebelum pengiriman, tetap mengikuti batas usia/akurasi. Alert bukan pelacakan latar belakang; fallback administratif tetap FR-05-07. Parameter geofence dari client tidak dipercaya. Snapshot bukti mencatat versi/nama/titik/radius dan jarak yang digunakan.

BAB IV. ATURAN BISNIS DAN ALUR PROSES
4.1 Periode dan riwayat
ID	Aturan
BR-01	Identitas siswa/pegawai tetap; keanggotaan kelas, jabatan, penugasan dan tarif memiliki periode efektif.
BR-02	Pergantian tahun ajaran tidak menghapus transaksi lama; laporan historis menggunakan keanggotaan/penugasan yang berlaku saat transaksi.
BR-03	Perubahan jadwal berlaku ke depan sesuai tanggal efektif; pertemuan terlaksana tetap menunjuk sumber historis.
BR-04	Waktu server menjadi acuan; timestamp kejadian UTC, tanggal/jam operasional Asia/Jakarta. Interval akhir eksklusif.

4.2 Jadwal, realisasi, dan verifikasi
Alur: penugasan → jadwal versi berlaku + kalender → pertemuan bertanggal → catatan guru pelaksana → verifikasi → JP yang memenuhi syarat → rekap honor.
Dimensi	Nilai / aturan
Pelaksanaan	Belum dicatat, terlaksana, tidak terlaksana. Penyebab batal disimpan terpisah.
Verifikasi	Belum diajukan, menunggu, disetujui, ditolak. Penolakan wajib alasan; pengajuan ulang mempertahankan riwayat.
Guru	Guru terjadwal dan guru pelaksana disimpan terpisah. Pengganti bukan status pelaksanaan.
JP yang diakui	Satu JP = 40 menit sebagai parameter awal; JP diakui = min(JP rencana, floor(menit aktual / 40 × 1000) / 1000). JP realisasi tidak melebihi rencana. Hitung uang dengan desimal presisi tinggi, bulatkan half-up ke rupiah per sumber, lalu jumlahkan; jangan bulatkan ulang total dengan metode lain. Hanya held + approved memenuhi syarat honor.
Perubahan realisasi	Sebelum locked: revisi/verifikasi ulang. Sesudah locked: revisi sumber melalui koreksi berizin dengan adjustment selisih; snapshot asal tidak berubah.

BR-05: satu realisasi aktif, satu guru pelaksana dan satu penerima honor per pertemuan; co-teaching nonaktif. BR-06: libur/kegiatan yang memblokir kelas mencegah JP honor otomatis; realisasi not_held bernilai nol dan beralasan. Data libur tidak ditafsirkan sebagai pegawai alpa.
4.3 Absensi siswa dan pegawai
BR-07: absensi harian pegawai tidak membuktikan realisasi mengajar; kedua proses tetap terpisah.
BR-08: baseline absensi siswa harian unik per siswa–tanggal; mode per pertemuan/both nonaktif dan hanya dapat diaktifkan melalui revisi policy.
BR-09: rekap menggunakan absensi harian saja. Ketiadaan catatan ditampilkan sebagai belum dicatat, tidak dikonversi otomatis ke alpa. Riwayat kelas mengikuti enrollment pada tanggal absensi.
BR-10: input siswa sampai 23.59 lokal; koreksi siswa/pegawai sampai 7 hari kalender memerlukan alasan dan persetujuan petugas berbeda. Setelah tenggat hanya izin koreksi terlambat eksplisit. Simpan sebelum/sesudah, pelaku, waktu, approval dan lock_version.
BR-24 (addendum absensi pegawai): foto dan GPS dikumpulkan untuk aksi check_in/check_out saja. Lokasi berupa latitude/longitude, akurasi dan waktu pengambilan; waktu kejadian absensi memakai server UTC. Default teknis: akurasi maksimal 100 m dan usia foto/lokasi maksimal 60 detik, tidak dari masa depan. Addendum v1.4: geofence opsional per policy; flag lama default false. Radius bukan akurasi GPS. Saat aktif, server memverifikasi jarak + ketelitian GPS <= radius; di luar atau meragukan ditolak 422 sebelum pemrosesan foto/penulisan absensi, termasuk request langsung ke API. Frontend memberi alert setelah GPS terbaca dan memeriksa ulang sebelum kirim; tidak ada bypass karena peta gagal dimuat. Geofence aktif wajib foto/GPS aktif, nama/titik lengkap dan radius 25–5.000 m. HTTPS serta izin kamera/lokasi wajib; izin ditolak, lokasi kedaluwarsa/tidak akurat, foto kosong atau kompresi gagal membuat aksi normal ditolak. Pegawai mengulang pengambilan; penanganan administratif hanya melalui petugas bermandat, alasan, approval/koreksi dan audit yang sudah berlaku, bukan membuat bukti kamera/GPS palsu. Foto/GPS bukan verifikasi biometrik atau jaminan anti-pemalsuan.
BR-25 (penyimpanan bukti): validasi dan kompresi foto selesai sebelum file final, metadata files, bukti dan waktu absensi dikomit. File final privat berformat WebP; database tidak menyimpan byte foto/base64. Satu bukti unik per absensi–aksi dan satu file tidak dipakai dua aksi. File sementara/asli dibersihkan; kegagalan database/storage tidak meninggalkan absensi sukses parsial. Bukti asli append-only dan tidak ditimpa koreksi; foto/GPS tidak masuk publik, portal wali, payload/log umum atau ekspor rutin. Akses hanya pegawai pemilik dan petugas absensi bermandat. Retensi mengikuti akademik/absensi 5 tahun setelah penutupan periode, tanpa penghapusan historis otomatis.
4.4 Honor dan penguncian
Rumus sumber dipertahankan: honor mengajar = JP memenuhi syarat × tarif; total = honor mengajar + tugas tambahan − potongan disetujui. Jika tarif berubah di tengah periode, hitung per sumber/tanggal memakai tarif yang berlaku, lalu jumlahkan.
ID / tahap	Ketentuan
BR-11 / Draf	Bendahara/petugas menghitung dari sumber yang memenuhi aturan, tarif berlaku, dan penugasan tambahan. Simpan snapshot nominal dan referensi sumber.
BR-12 / Diperiksa	Pemeriksa memvalidasi rincian. Kekurangan dikembalikan ke draf dengan alasan; revisi membatalkan persetujuan sebelumnya.
BR-13 / Disahkan	Kepala bermandat mengesahkan versi reviewed, berbeda dari pembuat dan pemeriksa.
BR-14 / Dikunci	Pengesahan langsung mengunci versi, rincian, sumber dan klaim secara atomik; approved_at dan locked_at disimpan pada commit yang sama.
BR-15 / Koreksi	Hasil locked tidak ditimpa. Default hanya adjustment selisih ke periode terbuka berikutnya; revisi pengganti locked nonaktif. Salah penerima menggunakan batch debit/kredit atomik.
BR-16 / Nilai uang	DECIMAL untuk penyimpanan dan aritmetika desimal presisi tinggi; half-up ke rupiah per sumber, total merupakan penjumlahan hasil sumber, tanpa floating-point.
BR-17 / Keunikan	Satu rekap aktif per pegawai–periode–jenis rekap; pengulangan hitung/permintaan tidak menggandakan komponen. Pengesahan paralel dicegah melalui transaksi dan kontrol konkurensi.
BR-18 / Pembayaran	Disahkan tidak berarti dibayar. Transaksi pembayaran digital di luar cakupan; pencatatan status bayar manual hanya ditambahkan melalui persetujuan kebutuhan.

Contoh uji: 72 JP × Rp25.000 + Rp300.000 + Rp500.000 = Rp2.600.000 tanpa potongan. Angka ini hanya fixture pengujian, bukan tarif produksi. Kalkulasi produksi memakai tarif nyata bertanggal dan default DEC-01–DEC-06; tarif yang belum tersedia menghasilkan kesalahan konfigurasi, bukan nominal tebakan.
4.5 BK, wali, konten, dan berkas
BR-19: BK membagikan ringkasan dengan penerima tertentu; catatan internal dan lampiran internal tidak ikut terbuka.
BR-20: hubungan wali–siswa memiliki status terverifikasi dan masa berlaku; pihak verifikator ditetapkan.
BR-21: publikasi membutuhkan izin penerbit; status arsip/draf menutup akses publik sesuai kebijakan.
BR-22: paket soal final menyimpan versi isi, urutan, dan kunci. Mengubah bank soal tidak mengubah paket final.
BR-23: master yang dirujuk transaksi dinonaktifkan atau diarsipkan; penghapusan fisik mengikuti retensi dan batas referensial. Soft delete tidak menggantikan kebijakan retensi.

4.6 Default historis, penyesuaian dan retensi
Kategori pegawai disimpan sebagai relasi bertanggal; satu kategori berlaku pada tanggal sumber honor. class_period menyimpan nama dan grade historis. Payroll sources menyimpan kategori/scope tarif terpilih agar perhitungan dapat diulang dengan fakta tanggal sumber.
Koreksi penerima membentuk adjustment batch berisi debit penerima asal dan kredit penerima benar, nominal transfer sama, source locked asal dan meeting yang sama, satu periode target terbuka yang sama. Kalkulasi ulang target menghitung efek kumulatif adjustment sebelumnya, bukan mengulang nilai asal. Kedua payroll target harus reviewed; approve batch mengunci keduanya dan menerapkan dua sisi dalam satu transaksi. Gagal salah satu sisi membatalkan keduanya. Klaim meeting asal tetap menyimpan fakta sumber honor yang disahkan, sementara koreksi ditelusuri lewat batch.
Kebijakan default disimpan sebagai baseline keputusan berversi dengan actor/time asal permintaan; persetujuan workflow bisnis tetap dicatat oleh akun nyata. Retensi DEC-15 adalah arsip teknis konservatif; disposal historis tidak otomatis. Data ekspor/impor sementara dibersihkan idempoten setelah kedaluwarsa; legal hold dan FK sumber diperiksa lebih dahulu.
4.7 Privasi, persetujuan, dan hak subjek data
BR-26: setiap kelompok data pribadi memiliki dasar pemrosesan tercatat; data pribadi anak hanya diproses untuk tujuan administrasi pendidikan dan tujuan lain hanya dengan persetujuan orang tua/wali yang sah. Persetujuan direkam dengan isi, waktu, pemberi persetujuan, dan versi dokumen persetujuan.
BR-27: permintaan hak subjek data (akses, perbaikan, pembatasan, keberatan) diverifikasi identitas pemohon, dicatat, dilayani sesuai tenggat kebijakan, dan hasilnya dilaporkan ke pemohon; penolakan diberalaskan dengan merujuk retensi/kewajiban hukum. Log permintaan tidak memuat isi data sensitif.
BR-28: penarikan persetujuan berlaku ke depan; konten yang telah terbit ditinjau dan ditarik dari akses publik pada siklus publikasi berikutnya. Retensi dan snapshot historis internal tetap mengikuti DEC-15 dan BR-23.

Target berikut menjadi default penerimaan pengembangan; ukuran kapasitas harus dibuktikan melalui uji, bukan dianggap terpenuhi oleh pilihan framework/server. Data nyata dapat mengganti profil melalui revisi NFR.

BAB VIII. ARSITEKTUR LARAVEL API DAN NEXT.JS/REACT
8.1 Arsitektur yang ditetapkan
DITETAPKAN: Laravel/PHP menjadi backend API modular monolith; Next.js App Router + React/TypeScript menjadi frontend. MySQL hanya diakses Laravel. Satu monorepo berisi backend/ dan frontend/, dengan PHP-FPM dan Node.js sebagai dua proses runtime yang dirilis terkoordinasi. Modul bisnis tetap di Laravel, bukan dipisahkan menjadi microservices.
Alur UI: browser → HTTPS/Nginx → Next.js untuk halaman dan BFF /api/{auth,accounts,master,academic,attendance,teaching,student-attendance}/* → Laravel /api/v1 melalui host API_BASE_URL tepercaya. BFF menyimpan JWT/refresh pada cookie HttpOnly dan menambahkan Authorization: Bearer hanya pada request server-ke-server yang memerlukan access token. Laravel guard api, Form Request, pemeriksaan akses dan layanan transaksi membaca MySQL lalu menghasilkan JSON Resource/DTO. Job validasi dan konfirmasi impor master sudah tersedia; worker ekspor/backup tetap pekerjaan modul berikutnya.
Controller Laravel menangani API dan memanggil layanan bisnis. Rumus honor, penomoran, verifikasi dan publikasi hanya di Laravel. Next.js membaca API dan mengelola tampilan; Route Handlers/Server Actions tidak menjadi tempat duplikasi aturan atau jalur tulis yang melewati otorisasi backend. Kontrak aktual /api/v1 mengikuti rute/controller/service dan tes modul selesai; OpenAPI lengkap tetap target integrasi, dengan kompatibilitas dijaga saat rilis.
8.2 Stack implementasi yang ditetapkan
Komponen	Pilihan	Tanggung jawab
Backend	Laravel + PHP	API /api/v1, guard api JWT, Google OAuth melalui Socialite, validasi, pemeriksaan akses, layanan bisnis dan transaksi. Laravel tetap sumber akun, sesi dan izin.
Kontrak integrasi	HTTP JSON + OpenAPI	Resource/DTO minimum, endpoint tujuh kelompok API sesuai §1.5, pagination sesuai endpoint, error 401/403/409/422/429/5xx, proteksi Origin BFF, serta idempotensi pada operasi domain yang menerapkannya. OpenAPI lengkap tetap pekerjaan integrasi berikutnya.
Frontend	Next.js App Router + React/TypeScript	UI, routing halaman, Server Components publik, Client Components interaktif dan akses API.
UI	Tailwind CSS + shadcn/ui	Komponen responsif, Bahasa Indonesia dan akses keyboard.
Database	MySQL 8.4 InnoDB + Eloquent	Hanya backend mengakses; relasi, histori, indeks, snapshot dan transaksi.
Build/runtime	Next.js build + Node.js LTS; Composer/PHP-FPM	Node.js runtime produksi untuk Next.js; PHP runtime untuk Laravel. Lockfile dan CI kompatibilitas.
Pekerjaan latar belakang	Laravel Queue database + scheduler	Impor/ekspor/backup; after-commit, retry terbatas dan monitor worker.
Deployment	Linux + Nginx TLS + PHP-FPM + Node.js	Satu monorepo, dua runtime; proxy satu origin publik, database privat, backup terpisah.

Backend memakai Laravel API dengan JWT HS256 dan Google OAuth opsional; frontend memakai Next.js App Router + React/TypeScript dengan Backend for Frontend (BFF). Laravel 13/PHP 8.4 dan Next.js 16/React 19 adalah keluarga versi proyek; patch dikunci composer.lock/pnpm-lock.yaml dan diuji pada lingkungan rilis. MySQL baseline 8.4. Tailwind CSS dan shadcn lokal digunakan konsisten sesuai design-system.md; komponen yang tersedia digunakan ulang sebelum membuat komponen baru.
8.3 Integrasi Laravel API–Next.js/React
Backend: gunakan Laravel routes, middleware, Form Requests, Policies, Eloquent dan transaksi. Action/Service mengelola aturan bisnis; queue worker dan scheduler diawasi. Redis ditambahkan hanya jika pengukuran menunjukkan kebutuhan.
Browser menggunakan BFF Next.js: madrasah_access dan madrasah_refresh disimpan sebagai cookie HttpOnly, host-only, Path=/, SameSite=Lax; Secure aktif pada production. Max-Age cookie mengikuti sisa refresh_expires_in, sedangkan masa sah JWT tetap expires_in. Mutasi BFF mewajibkan Origin sama dengan APP_URL dan Content-Type application/json; unggah CSV master dan foto clock absensi menggunakan multipart/form-data pada rute yang diizinkan; kegagalan ditolak 403. Laravel menerima access token melalui Authorization: Bearer dari BFF. Access default 15 menit, sesi/refresh absolut 120 menit sejak login, tanpa idle sliding atau remember-me. CORS Laravel berisi allowlist origin dengan supports_credentials=false; cookie sesi Laravel hanya untuk transaksi OAuth Google, bukan login API utama.
API Resource/DTO hanya mengembalikan field yang dibutuhkan dan diotorisasi. BK internal, kunci soal dan siswa lain tidak boleh ikut respons/props tanpa izin objek yang sesuai. Halaman privat saat ini membaca profil melalui server helper auth/me; data dan mutasi modul selesai melewati BFF area terkait. Fetch personal no-store dan tidak memakai cache lintas pengguna. API domain selesai memeriksa tindakan/objek di Laravel melalui DataAccess/service. Modul berikutnya wajib mempertahankan batas yang sama.
Formulir React memakai validasi UX dan HTTP client terpusat; Laravel menentukan validasi/izin. Respons 422 untuk field, 401 untuk autentikasi gagal, 403 untuk izin atau Origin BFF ditolak, 409 untuk konflik lock_version, 429 untuk rate limit; fitur nonaktif/tidak tersedia dapat mengembalikan 404. Timeout/upstream error BFF memakai pesan aman 5xx. Pengelolaan akun memakai lock_version; domain lain memakai versi/timestamp atau ID policy/revisi yang diharapkan sesuai kontrak. Idempotency-Key tersedia pada clock absensi dan operasi pencatatan terkait; bukan persyaratan universal untuk seluruh mutasi. Daftar akun saat ini 15/baris dan audit akun 20/baris.
Frontend memakai frontend/app untuk App Router dan route BFF, components/ui untuk shadcn lokal, components/layout/auth/accounts dan direktori fitur master/academic/attendance/teaching/student-attendance untuk komponen, serta lib area terkait untuk kontrak/helper HTTP. Server Component memakai requireUser dan batas Suspense; Client Component memakai endpoint BFF same-origin. Komponen digunakan ulang sesuai design-system.md. Modul website publik/SSR dan cache data terbit masih rencana; secret tetap server-side tanpa prefix NEXT_PUBLIC_.
8.4 Deployment, berkas, dan operasional
Development → staging → production memakai monorepo dan konfigurasi terpisah. CI/rilis memeriksa tes Laravel dan lint/typecheck/build Next.js sesuai cakupan perubahan. Nginx meneruskan /api/v1/* ke PHP-FPM Laravel; seluruh route BFF pada §8.1, halaman dan aset ke runtime Next.js. BFF menggunakan API_BASE_URL tetap. HTTPS, konfigurasi proxy, worker/scheduler, backup, deployment dan API publik /api/v1/public tetap harus dibuktikan pada staging/implementasi domain terkait.
Storage publik untuk konten yang sudah diterbitkan. BK, honor, soal/kunci dan arsip terbatas disimpan privat; unduhan melalui otorisasi atau URL sementara setelah pemeriksaan izin.
Ekspor memiliki pemilik, cakupan akses, masa berlaku dan pembersihan. Pencabutan izin harus dipertimbangkan saat pengguna mengunduh hasil lama.
Queue Laravel memakai driver database, timeout job awal 300 detik, retry maksimal 3 kali dengan backoff dan retry_after lebih besar dari timeout. Job dikirim setelah commit dan idempoten. Render PDF, impor dan backup berjalan di worker, bukan request API/halaman. Snapshot laporan diekstrak dalam consistent snapshot MySQL sebelum render berkas; cutoff awal tidak cukup untuk membekukan nilai yang sedang dikoreksi.
Backup database dan berkas wajib terenkripsi, checksum/manifest konsisten dan salinan terpisah; kunci disimpan terpisah dari backup. Default harian dan retensi/restore sesuai DEC-14, dengan log keberhasilan/kegagalan di luar database produksi.
Git dan pemeriksaan rilis digunakan. Node.js Next.js, PHP-FPM, worker/scheduler dan MySQL dipantau. Notifikasi kegagalan hanya metadata aman ke pengelola yang dikonfigurasi. Pemisahan worker/database dilakukan berdasarkan pengukuran.
8.5 Catatan keputusan arsitektur (ADR)
ADR mencatat konteks, alasan, konsekuensi, pemilik dan tanggal. ADR-01 menetapkan Laravel API + Next.js/React + MySQL; ADR-02 diperbarui 20 Oktober 2026 mengikuti permintaan JWT + Google OAuth dengan BFF dan cookie HttpOnly; ADR-03 snapshot honor/paket; ADR-04 snapshot laporan. DEC-08 dan DEC-13 diselaraskan pada implementasi autentikasi; aturan bisnis non-auth dan snapshot historis tetap.

8.6 Kontrak API, cache dan kompatibilitas rilis
GET /api/v1/auth/me menyediakan profil, role aktif, permissions akun/master/akademik dan navigation; izin verifikasi/koreksi efektif tetap diperiksa layanan domain; BFF mengekspos pemeriksaan sesi melalui GET /api/auth/session. API accounts memakai meta page/last_page/total dengan 15 baris akun dan 20 baris audit. Kelompok domain yang tersedia dirangkum pada §1.5; parameter pagination dan idempotensi mengikuti controller/service masing-masing. Endpoint /api/v1/public dan OpenAPI lengkap belum tersedia. Konflik versi akun maupun revisi/policy domain menghasilkan 409 sesuai kontrak.
GET personal dan unduhan privat memakai Cache-Control: private, no-store. Middleware API Laravel dan respons BFF modul privat menerapkan kebijakan privat; request personal ke Laravel memakai cache: no-store. Autentikasi Server Component memakai cookies/connection dan memoization hanya selama request, dengan batas Suspense. Respons Set-Cookie/auth melewati cache proxy/CDN. API publik/pencabutan aset dan invalidasi cache masih harus diuji saat modul publikasi dibuat.
Laravel memiliki akun, auth_sessions, auth_refresh_tokens, oauth_accounts dan otorisasi. Next.js tidak memiliki database identitas/session terpisah; ia mengelola cookie browser dan menjembatani HTTP ke Laravel. Pembacaan sesi halaman memanggil auth/me; pembaruan token berjalan melalui route BFF, dengan deduplikasi refresh 15 detik dalam satu proses Node.js. Multi-instance memerlukan koordinasi/peninjauan tersendiri. Secret ENV backend/BFF tidak memakai NEXT_PUBLIC_ dan tidak dikirim sebagai props atau log.

FR/BR dan kriteria penerimaan terkait jelas; UI, validasi, izin objek, kegagalan, serta audit sesuai kebutuhan.
Migration dan perubahan data dapat dijalankan di staging; tes kritis lulus dan hasil ditinjau.
Pengguna terkait mencoba contoh realistis; dokumentasi/keputusan diperbarui.
Tidak ada cacat kritis yang membuka data sensitif atau mengubah perhitungan tanpa jejak. Temuan lain memiliki prioritas dan pemilik.
9.3 Pilot dan rilis
Pilot diusulkan pada satu kelas/kelompok pegawai selama satu siklus absensi; untuk honor, rekonsiliasi satu periode lengkap sebelum mengandalkan hasil aplikasi. Jalankan pembandingan dengan pencatatan yang digunakan madrasah, selesaikan selisih, lalu perluas pengguna.
Checklist rilis: versi/backup, migrasi diuji, worker/scheduler aktif, health check, izin/HTTPS/debug, data awal, panduan, kontak pengelola, pemantauan, rencana pembatalan, laporan uji keamanan independen (NFR-16), dan hasil budget performa frontend (NFR-15). Rollback memperhitungkan transaksi baru serta kompatibilitas skema; pemulihan backup bukan dilakukan otomatis tanpa mempertimbangkan kehilangan data setelah backup.

10.1 Strategi tes
Unit: rumus DEC-01–DEC-05, prorata, pembulatan per sumber, tanggal efektif dan transisi status.
Integrasi/fitur: transaksi database, unique constraint, izin per objek, snapshot dan worker.
End-to-end/UAT: alur guru, bendahara, BK, TU dan wali pada browser/perangkat representatif.
Kapasitas/operasional: beban campuran, permintaan paralel, gagal queue, restore dan rilis percobaan.
Keamanan/privasi: otorisasi objek, BFF/cookie/token, unggahan berkas, halaman publik dan konfigurasi server; uji keamanan independen (NFR-16) menjalankan kembali skenario negatif utama, dan persetujuan publikasi diuji pada AC-40.
Prioritaskan risiko bisnis: kebocoran siswa/BK/honor, JP ganda, perubahan riwayat dan hasil honor. Pengujian dilakukan pada tiap tahap, kemudian regresi akhir.

11.1 Risiko dan mitigasi
Risiko	Mitigasi
Aturan honor berubah setelah kode dibuat	Simpan versi default/rate bertanggal, contoh hitung dan tes; perubahan tidak menimpa snapshot.
Data siswa/BK terbuka lewat URL atau ekspor	Otorisasi objek/cakupan, storage privat, uji negatif semua jalur baca.
Data pribadi diproses atau diterbitkan tanpa dasar/persetujuan (UU PDP)	Register dasar pemrosesan, persetujuan berversi per siswa, pemeriksaan otomatis sebelum terbit, layanan hak subjek data, dan uji keamanan independen prarilis.
Master/riwayat ditimpa	Identitas tetap, periode efektif, versi jadwal dan snapshot transaksi.
Akun ganda atau impor berulang	ID sumber, laporan kandidat duplikasi, batch impor, unique constraint.
Laporan membebani server	Queue, paginasi/indeks, pembatasan pekerjaan dan uji beban.
Backup tidak bisa dipakai	Salinan terpisah, log, pemulihan terukur dengan data dan berkas.
Stack sulit dipelihara pengelola	Pelatihan Laravel API/Next.js, JWT/refresh token, Google OAuth state/PKCE, cookie HttpOnly dan proteksi Origin BFF; proses PHP/Node.js, lockfile, CI dan runbook.

11.2 Pengendalian perubahan
Usulan perubahan mencatat pemohon, alasan, kebutuhan yang terdampak, dampak data/akses/biaya/jadwal, kriteria penerimaan, keputusan dan versi. Perubahan cakupan disetujui pemilik kebutuhan; pilihan teknis rutin dicatat pengembang sesuai mandat. Tidak mengklaim pengesahan sebelum bukti persetujuan tersedia.

LAMPIRAN A. GLOSARIUM
Istilah	Makna
JP	Jam pelajaran; default awal 40 menit per JP, perubahan memakai versi policy efektif.
Jadwal	Pola kegiatan berdasarkan penugasan dan periode efektif.
Pertemuan	Kejadian pembelajaran pada tanggal/slot tertentu.
Realisasi	Catatan pelaksanaan pertemuan oleh guru pelaksana.
Snapshot	Salinan nilai/versi yang digunakan saat transaksi agar riwayat tidak berubah akibat master terbaru.
Modular monolith	Backend Laravel dibagi modul domain; frontend Next.js terpisah runtime dalam satu monorepo, seluruh transaksi bisnis dan database dimiliki backend.
Idempotensi	Pengulangan operasi tidak menghasilkan efek tambahan yang tidak diinginkan.
RPO / RTO	Batas kehilangan data berdasarkan waktu / target waktu pemulihan layanan.
UAT	Pengujian penerimaan oleh pengguna/pemilik proses.
ADR	Catatan keputusan arsitektur dan konsekuensinya.
Queue/worker	Antrean pekerjaan dan proses yang mengerjakannya di latar belakang.
JWT / refresh token	Access token bertanda tangan untuk API dan token acak sekali pakai untuk rotasi; keabsahan tetap diperiksa terhadap sesi Laravel.
BFF	Backend for Frontend pada route Next.js: mengelola cookie HttpOnly dan meneruskan request ke Laravel tanpa menyimpan database identitas sendiri.
OAuth state / PKCE	Pengikatan transaksi login Google untuk menolak callback palsu, tertukar, diulang atau kedaluwarsa.
Persetujuan (consent)	Pernyataan izin orang tua/wali yang direkam berversi untuk pemrosesan atau publikasi tertentu; dapat ditarik dan penarikan berlaku ke depan.
Hak subjek data	Hak pemilik data pribadi untuk mengakses, memperbaiki, membatasi, dan mengajukan keberatan atas pemrosesan datanya, dilayani petugas berizin sesuai BR-27.
